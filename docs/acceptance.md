# MenuGo — критерии приёмки и проверяемость

Статус: аудит этапа 12.0 и критерии для будущих отдельных заданий. Чтение тестового кода **не равно** успешному запуску. На этапе 12.0 тестовые базы, Cloudinary, Telegram, email и банк не вызывались; результаты прежних запусков из README здесь не переобъявляются как свежие.

## Приёмка этапа 12.0

- Созданы `docs/product-spec.md`, `docs/architecture.md`, `docs/roadmap.md`, `docs/acceptance.md` на русском языке; они ссылаются друг на друга и различают текущий код, целевую спецификацию и открытые решения.
- Указаны фактические модели/индексы и маршруты по `server/src`, текущие роли owner/staff, денежные и статусные инварианты, серверные зависимости; целевые admin/Telegram/billing/outbox не обозначены как готовые.
- Описаны Free/Pro, однократный trial, ручное подтверждение банковского платежа, оплата еды официанту, план миграции и rollback; прямо указано, что тарифы и подписки пока не реализованы.
- Указаны реальные тестовые скрипты и пределы их покрытия, mock и отдельные MongoDB verification базы; не утверждается, что в 12.0 выполнялись browser/E2E или реальные провайдеры.
- Существующие незакоммиченные QR-правки сохранены, но не признаны готовым API. В рамках 12.0 не изменяются `client/`, `server/`, `README.md`, package/lock, `.env`, база или системные настройки; push/deploy не выполняются.

## Существующие средства проверки

Команды перечислены для последующих этапов; **в этом документальном аудите они не запускались**. Серверные скрипты создают записи в отдельных именованных базах через `MONGO_URI`. Перед запуском нужно убедиться, что URI относится к тестовому кластеру и выдаёт разрешение на эти базы; скрипты не служат тестом против production.

| Команда | Зависимость | Что проверяет код скрипта | Чего не доказывает |
| --- | --- | --- | --- |
| `cd client; npm run typecheck` и `npm run build` | Локальные пакеты | Типы и сборка React/Vite | Поведение браузера, MongoDB и QR-сканер |
| `cd client; npm run verify:receipt` | Node; без БД | Пять статусов receipt, русский текст и отказ неизвестному статусу/неверной сумме | Реальное получение заказа |
| `cd client; npm run verify:orders-panel` | Node; без БД | Потерянный PATCH + старый GET, блок действий до свежей проверки | Весь DOM, фокус, серверные гонки |
| `cd client; npm run verify:tables` | Node; mock fetch | Точный QR URL, печатный SVG, CSRF/credentials, ответы ошибок | Сканирование на устройстве, реальный GET/POST таблиц; при текущем незавершённом QR diff тест и API могут не совпадать |
| `cd server; npm run typecheck` и `npm run build` | Локальные пакеты | Типы и компиляция Express/TS | Поведение MongoDB, внешние провайдеры |
| `cd server; npm run verify:auth` | `menugo_stage81_verification` | Argon2id, cookie/SID/CSRF/Origin, owner/staff, отзыв доступа, 429/503, отказ индекса session store и восстановление, public API | Email activation/reset, отдельный admin scope |
| `cd server; npm run verify:orders` | `menugo_stage6_verification` | Снимки цен, `PRICE_CHANGED`, ошибки, другие кафе, последовательные/параллельные идемпотентные повторы, 429/503 | Платёж, guest tracking, Telegram |
| `cd server; npm run verify:manage-menu` | `menugo_stage91_verification`; Cloudinary **mock** | CRUD без удаления, изоляция, public visibility, снимок старого заказа; формат/размер фото, ошибки upload/DB, pending cleanup и параллельные действия | Реальный Cloudinary, тарифные ограничения, состав/варианты блюда |
| `cd server; npm run verify:manage-orders` | `menugo_stage101_verification` | Фильтр, страницы, переходы, параллельный PATCH, снимок, CSRF/Origin, роли/кафе | Назначения столов официантам, бот, гостевой tracking |
| `cd server; npm run verify:manage-tables` | `menugo_stage11_verification` | Создание/редактирование/выключение, QR, дубли и параллельные запросы, guest menu, снимок, граница кафе | Все старые короткие QR, реальная печать/сканирование, незавершённый новый QR контракт |

В репозитории есть три клиентских test-файла и пять серверных verification-скриптов. Полного автоматического браузерного набора нет. В `verifyManageMenu.ts` изображение подменяется mock storage; этот тест не загружает реальные файлы в Cloudinary. Для живого end-to-end нужна отдельная тестовая база, безопасные provider sandbox/учётные данные и явное разрешение на взаимодействие с ними.

## Критерии для существующих сценариев при следующих релизах

| Сценарий | Принимается, если |
| --- | --- |
| Гостевой QR | QR содержит ровно URL `https://<origin>/menu/<cafeSlug>/<tableCode>` без Mongo ID/секретов; сканирование открывает нужный активный стол, выключенный/чужой стол даёт `404`; старый напечатанный QR имеет согласованную судьбу |
| Публичное меню | Возвращаются только данные своего активного кафе, активных категорий и доступных блюд; порядок стабилен, ID — строки, внутренние поля скрыты; без БД `503` |
| Корзина | Кафе и стол изолированы по ключу, количество 1–99, сумма точная, отсутствующее блюдо удаляется с сообщением, ошибка меню не показывает ложные старые данные |
| Создание заказа | Сервер рассчитывает сумму по БД, 1–50 различных позиций, целые цены KGS; новый `201`, тот же `requestId`/состав `200` и тот же ID даже после смены статуса/цены; другой состав `409`, новая устаревшая цена `409 PRICE_CHANGED` без записи |
| Статус в кабинете | Только допустимые `new→preparing→ready→completed` или отмена из первых трёх; `expectedStatus` + атомарное обновление; проигравший параллельный PATCH `409`; order snapshot не меняется |
| Безопасность кабинета | Сессия MongoDB и CSRF, точный Origin, повторная проверка активности и роли; `staff` не управляет меню/столами, owner не видит чужое кафе; login/logout не раскрывают секреты |
| Изображения | MIME + сигнатура JPEG/PNG/WebP до 5 MiB; чужое блюдо недоступно; при конфликте параллельных операций текущее фото не теряется, pending IDs сохраняются внутри базы и очистка не удаляет актуальный файл |

Для UI повторить проверки на 375, 390, 768, 820 и 1440 px: прямой URL/refresh, клавиатура, Escape/возврат фокуса, reduced motion, loading/empty/offline/error и сохранение несохранённой формы. Автоматические mock тесты дополняют, но не заменяют проверку сканирования QR настоящим телефоном на том же доступном origin.

## Критерии для целевых функций: ещё не выполнены

### Заявки, идентичность и доступ

- Заявка не запускает trial. Администратор с **отдельным** scope видит только разрешённые данные, принимает решение и оставляет аудит; отказ содержит причину. Нет публичной регистрации администратора и фиктивного cafeId.
- Пароль задаётся по одноразовому email-токену: в базе только digest, срок проверяется при потреблении, из параллельных запросов проходит один. Reset отзывает прежние сессии. Наличие email не раскрывается. В логах/URL аналитики/ответах нет токена и пароля.
- Владелец видит своё кафе; официант — только назначенные заказы. Изменение назначения, роли или активности действует на уже открытые сессии/бот callback. Неправильный Telegram user ID не даёт доступ.

### Тариф, trial и биллинг

- Единый серверный тарифный контракт отдаёт клиенту цену/лимиты/разрешённые функции. Free: 0 KGS и без срока; Pro: 1500 KGS за календарный месяц, trial 30 дней максимум один раз на кафе, включая первый переход Free → Pro. Повторная заявка/смена тарифа trial не возрождает.
- Истечение определяется сервером по UTC на каждом запросе, даже без cron. После истечения effective plan Free; старые заказы и данные сохраняются, превышающий лимит существующий контент не скрывается, новые добавления/активации блокируются. Admin block проверяется отдельно.
- Free запрещает новый upload/замену фото **на backend**, исключает `imageUrl` из public menu, показывает локальный SVG; старый файл сохраняется, owner может удалить его. Pro снова видит сохранённое фото. Логотип кафе работает на обоих планах.
- Проверка лимитов 30/50 активных столов, 20 официантов, 100/300 блюд защищена от параллельных созданий и включений. Client не передаёт эффективный тариф как источник истины.
- Оплаченный период начинается от текущего `periodEnd` для активного Pro, после истечения — от подтверждения; одинаковый bank reference/платёж продлевает **ровно один раз**. Тесты охватывают 29/30/31 число, февраль и високосный год после утверждения календарного алгоритма из спецификации. Интерфейс показывает `Asia/Bishkek` по-русски.
- Скриншот без проверенной банковской транзакции не переводит платёж в подтверждённый. Гость платит за еду официанту; нет карточного checkout для еды и нет утверждений об автоматическом списании за Pro.

### Заказ, доставка и интеграции

- Гостю выдаётся право смотреть только его заказ, без доступа к остальным заказам стола по одному QR. Повтор и refresh работают, токен/право имеет срок и безопасное хранение; отсутствие сети показывает неизвестный результат без нового заказа.
- Состав/варианты/добавки и время приготовления проходят серверную валидацию и сохраняются в snapshot; старые `Order.items` продолжают читаться. Термины статусов согласованы с официантом до изменения автомата.
- Событие заявки/заказа/платежа и соответствующий outbox создаются в одной MongoDB transaction. Остановка Telegram/email не теряет бизнес-запись; рестарт worker продолжает lease, retry/backoff и dead-letter. Тот же event и provider retry не повторяют заказ/платёж, хотя дубли внешнего уведомления возможны.
- Миграция сначала проходит dry-run на копии, показывает конфликты, проверяет backup/restore и rollback; повторный запуск не дублирует сущности и не удаляет реальные данные. Проверить совместимость старых QR, заказов, пользователей и фото.

## Необходимые среды и отчёт о проверках

Будущие реальные проверки требуют отдельно подготовленных: MongoDB verification database/кластера, тестового Cloudinary (только для фото), email sandbox, Telegram test-бота и контролируемого банковского подтверждения; production credentials не помещаются в Git/README/логи. Выбор email/Telegram/банковского провайдера и разрешение на создание платных ресурсов остаются открытыми. В каждом отчёте явно указывать, что было **mock**, что было выполнено на реальной отдельной базе/провайдере, что не проверено, и какое состояние оставлено в Git.
