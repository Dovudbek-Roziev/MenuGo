# MenuGo — дорожная карта после аудита 12.0

Этот документ **план**, а не разрешение начинать следующие этапы. На этапе 12.0 создаются только четыре документа в `docs/`. Приоритет — сохранить работающие лендинг, гостевой заказ и кабинет, затем добавлять функции небольшими проверяемыми частями. Для каждого этапа нужны отдельное задание, миграция при изменении данных и критерии из [acceptance.md](acceptance.md).

## Состояние репозитория на момент аудита

Уже есть публичное меню и заказ с идемпотентностью, сессионный вход owner/staff, управление меню/фото/столами и панель заказов. Источник — [architecture.md](architecture.md). Одновременно локально оставлены **незавершённые незакоммиченные** изменения QR API и клиента. Их нельзя считать завершённым этапом: прежде чем добавлять новые функции, нужно отдельным заданием согласовать исправление или откат, воспроизвести проблему старых коротких QR, проверить уже распечатанные ссылки и клиентские тесты.

## Последовательность будущих работ

| Очерёдность | Результат | Зависимости и условия выхода |

## Порядок работы внутри каждого этапа

1. Утвердить HTTP контракт, бизнес-инварианты и права. Вопросы из [product-spec.md](product-spec.md) фиксировать явно.
2. Зафиксировать модель, индексы и миграцию с dry-run, повторяемостью, backup и проверяемым rollback. Для денежного периода использовать целые KGS и UTC.
3. Добавить service/policy и route/adapter. Авторизация и граница кафе проверяются сервером, не по `role`/`cafeId` из клиента.
4. Проверить backend на отдельной базе: нормальный сценарий, конкуренция, отказ провайдера, утечки между кафе, регрессия guest order.
5. Подключить клиент, затем проверить браузер и клавиатуру на 375, 390, 768, 820 и 1440 px. Сохранить дизайн и введённые данные при ошибке.
6. Обновить русские документы и сообщить фактически выполненные проверки отдельно от mock. Push/deploy/оплачиваемые ресурсы — только по отдельному поручению.

## Решения, нужные до реализации

| Вопрос | Почему блокирует проектирование |
| --- | --- |
| Правило прибавления календарного месяца с 29–31 числа и после февраля | Нужны проверяемые `periodStart/periodEnd`, единичное продление и ожидаемый срок для владельца |
| Идентификация одного кафе при повторной заявке | Предотвращает повторный 30-дневный trial и двойное владение |
| «Активные блюда» и «активные официанты» | Влияет на подсчёт лимитов Free/Pro и сохранение избыточных старых записей |
| Привязка существующего `staff` к роли официанта и назначениям | Сейчас `staff` видит все заказы кафе; целевое право уже |
| Значение `completed` и «доставлен», подтверждение приёма | Нельзя переименовать статусы без совместимости старых заказов и клиента |
| Гостевой ключ отслеживания и его срок | Публичный QR не должен открывать другие заказы стола |
| Банк, email-провайдер, Telegram-бот, домен | Нужны отдельные credentials, безопасная доставка и тестовая среда; реальные ресурсы в 12.0 не создаются |
| Политика старых QR и печатных материалов | Замена кода может обнулить уже размещённый на столе QR |
